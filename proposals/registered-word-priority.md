# 利用者の辞書に登録した綴りを、区切りの点で比べずに優先する

段階: 2 試行

## 問題

- `node` を Node.js として登録して `node` と打つと、「ので」になる
- `github,node` と打つと、末尾の node が Node.js にならず「GitHub,ので」になる。後ろに日本語が続けば（`nodewoinsuto-rusuru`）Node.js になる

英語まじりの日本語では複数形（`nodes`）を打たないので、複数形は扱わない。

## 原因

登録した英語の語の区間は、ほかの読み方と区切りの点で比べるだけで、勝つ保証が無い。点を利用者の語 1 つ分より下げない（max(綴りの点, 登録語の点)）だけである。

- `node` だけのときは、登録語の候補（Node.js）は入るが、genmai が文として「ので」を選ぶ。genmai は利用者の辞書を知らない
- `github,node` のときは、英語の後の読点は英語区間に含めるので「github,」が英語区間になり、英語区間は英語区間に続けられないため、node は日本語にしかなれない。main では「github,node」全体の英語区間が勝っていたが、入力の先頭を文の始まりとして読むようにしてから、日本語の「ので」の点が上がって負けるようになった

## 決まりの案

登録した打鍵（英語の語と、日本語として登録した読めない打鍵）とちょうど一致する範囲のうち、両側が区切りの端（部分の先頭か末尾、句読点、空白）のものには、日本語区間を重ねない。区切りの候補はこの条件を満たすものだけを作り、genmai はその中から選ぶ。語の途中で一致したものは、今までどおり点で比べる。

## 基づく原則

未定。利用者の発言は「辞書にあるなら辞書を優先でマッチさせるべきだ」「打鍵で登録してるんだから打鍵にマッチすれば優先候補にする」。docs/how-it-works.md も「tugime の辞書に登録した打鍵は、上の規則より優先する」と書いている。

## 出所

発明。

## 効果

`tugime-cli --dictionary`（node・github・tugime・cafe を英語、sake を日本語として登録）の `--typing` で確かめた。

| 打鍵 | 打ち終えた表示 |
|---|---|
| node | Node.js |
| github,node | GitHub,Node.js |
| sukinanodesu | 好きなのです（語の途中の node は優先しない） |
| nodewoinsuto-rusuru | Node.jsをインストールする |
| githubdekoukaisuru・tugimewotukau・sakewonomu・cafedeyasumu | GitHubで公開する・tugimeを使う・鮭を飲む・Caféで休む（変わらない） |

辞書を使わない 24 文は、498 打鍵すべて表示が変わらない。`swift test` はすべて通る。

## 弱点・反例

- 部分の末尾も区切りの端に含めるので、`node` で始まる日本語（`nodesu`、のです）を打ち進めると、`node` の時点で Node.js が出て、続けて打つと「ので…」になる
- 後ろに日本語が続く所は優先しないので、`nodewo` まで打つ途中は「のでを」になり、`nodewoin` で「Node.jsをイン」に戻る
